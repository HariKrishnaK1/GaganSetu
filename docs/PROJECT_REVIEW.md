**GaganSetu code review — 12 September 2026**

The application builds successfully and its main simulation flows work. The most important correctness issues are departure from a closed origin, results that depend on playback step size, and route history that loses turns. UI accessibility and responsive layout also need attention.

This review read all 1,075 lines across the eight application TypeScript/TSX/CSS files, plus project configuration and documentation. SVG assets were inspected for structure and active content; all four raster assets were viewed. The lockfile's 99 package entries were checked structurally. Installed third-party code in `node_modules` and generated/minified output in `dist` were not audited line by line. A build regenerated `dist` and TypeScript build metadata; application source was not changed. No deployment was performed.

**Confirmed model findings, in priority order**

1. **Medium — A closed departure pad does not prevent take-off.** `src/model/simulator.ts:58` starts any `ready` simulation, subtracts take-off energy, then checks the destination and alternatives. It never checks the origin's actual or received status. Reproduction: create a normal scenario, close P01 using `changePadStatus`, start, and advance 10 seconds. The aircraft remains `flying` and travels 0.3333 km although P01 is closed. The UI permits this sequence through its selected-pad control. Define whether closure prohibits departure and, if it does, check it before charging take-off energy. If closures are intended to prohibit only landing, the UI and model contract should explicitly say that.

2. **Medium — Playback speed changes simulation results.** At `src/model/simulator.ts:117`, the clock advances before closure processing, message receipt, reconsideration, and movement. An event at the end of an interval can affect movement for that entire interval. Closures and heartbeats also compare floating-point time without the tolerance used for message receipt. `src/App.tsx:44` passes 0.1-second steps at 1× and one-second internal steps at faster speeds. With the default closure scenario, 0.1-second calls landed at P02 at 170.9 seconds, after 5.696623 km, with 23.603377 kWh. One-second calls landed at P02 at 169 seconds, after 5.629958 km, with 23.670042 kWh. Even normal-flight arrival is reported at 526.1 versus 527 seconds. Split advancement at event and arrival boundaries, or use a consistent internal clock independent of playback frequency. Regression checks should compare outcomes across step partitions.

3. **Medium — History drops intermediate corridor vertices and diversion turns.** `src/model/simulator.ts:126` saves only the final position of an entire `advanceSimulation` call, and only if it is more than 10 metres from the last sample. Node arrivals at line 109 are not recorded. Calling `advanceSimulation(state, 3600)` for the normal default route produced only two history points, despite traversing P01 → P02 → P04 → P06 → P07. Actual distance was 17.534392 km; the straight line between history endpoints was 15.762650 km. Both map views draw this incomplete history and the export includes it. Ordinary multi-second calls also cut corners near vertices. Record every reached vertex and direction change, and always retain the terminal position; apply sampling only to straight segments.

4. **Low — Post-landing feasibility is misleading if read as another flight.** `src/model/simulator.ts:42` subtracts take-off energy only for `ready` states. After landing, options still display using the remaining battery and a new landing charge, without a new take-off charge. `src/App.tsx:151` and the options panel continue showing these counts. Either freeze/label these as end-of-flight diagnostics, hide them for terminal states, or calculate a separate next-flight budget.

5. **Low — Horizon failure has no matching event.** `src/model/simulator.ts:132` sets `blocked` and a failure reason after one hour but does not append an error event. This is reachable with valid low-speed custom configurations, although the present UI fixes speed at 120 km/h. Keep the state outcome and exported event log consistent.

**UI and integration findings from source inspection**

These findings were traced in JSX/CSS, but were not verified in a rendered browser: the available computer-use tool reported that no browser was available.

- **Medium — Collapsed sidebar controls remain keyboard-focusable.** `src/App.css:161` uses zero width, opacity, overflow, and `pointer-events: none`; the subtree stays mounted at `src/App.tsx:73`. Those styles do not remove links, buttons, inputs, and selects from keyboard navigation. Apply `inert`/appropriate hiding when collapsed and restore focus to the toggle when collapsing from inside the sidebar. Put `aria-expanded` and `aria-controls` on the controlling button, not only the aside.
- **Medium — Floating controls can overlap or be clipped.** `src/App.css:273` places the toolbar at a fixed 470px offset while line 287 independently anchors a 320px options panel at the top-right, at the same stacking level. Both may occupy the same space. Below 980px, line 388 changes the toolbar to `position: static`, so its z-index no longer lifts it above the absolutely positioned map in the ordinary block layout. The fixed failure-toast offset at line 352 has no small-screen override. Use coordinated grid/flex regions and verify all combinations of visible panels at desktop, tablet, and mobile widths.
- **Medium — Mobile header has no wrapping or compact treatment.** `src/App.css:213` lays out breadcrumb, five symbol controls, and actions in one row. The mobile media query only rearranges the sidebar/map. At narrow widths, these controls compete for insufficient space while outer containers hide overflow. A 340px body minimum also prevents fitting a 320px viewport. Check 320/375/768/980px widths and enlarged text.
- **Low — Core playback is hidden on initial load.** All four overlay flags default to false at `src/App.tsx:23`. The Start button exists only inside the playback overlay at line 159. The header Play symbol opens that overlay rather than starting a flight. Keep the primary start action visible or make the two-stage interaction explicit.
- **Low — Toggle states are not exposed consistently.** Overlay buttons at `src/App.tsx:99` and map-view buttons at line 181 indicate selection through CSS but omit `aria-pressed` or associated expanded state. Leaflet pad markers at `src/MissionMap.tsx:41` omit distinct accessible names. The SVG schematic supplies pad names and keyboard handling, but its parent `role="img"` should be checked with a screen reader because the SVG also contains interactive descendants.
- **Low — Theme persistence can break rendering when storage is unavailable.** `src/App.tsx:27` calls `localStorage.getItem` during initialization, with no exception handling, and casts arbitrary stored text to the theme union. Line 39 also writes without handling failures. Validate the stored value and use a guarded fallback. `src/index.css:20` follows the system color scheme while the app theme is independently selected; synchronize native control color scheme with the selected theme.
- **Low — Export is a summary, not a reproducible state snapshot.** `src/App.tsx:64` omits current actual pad states, queued notifications, current route state, and per-trial histories/events. A manually changed in-progress mission cannot be restored directly from the file. Define the export contract and include these fields only if replay/restoration is intended. Its history also inherits the confirmed sampling defect above.
- **Low — Automation registration failures disappear silently.** `src/webmcp.ts:10` suppresses both synchronous and asynchronous registration errors. Feature detection is appropriate, but registration failures on a supported browser deserve development diagnostics. The use of `document.modelContext` and an AbortSignal lifecycle agrees with the current [Chrome WebMCP documentation](https://developer.chrome.com/docs/ai/webmcp/imperative-api); it should not be replaced based on older navigator-based examples. Native tool execution and StrictMode lifecycle behavior still need browser testing.
